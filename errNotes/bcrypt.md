## 一、为什么密码不能明文存储

最基本的安全原则。数据库一旦泄露（SQL 注入、备份泄露、内部人员），明文密码直接暴露。

更严重的是**密码复用**：用户在 A 站用同一个密码注册了邮箱、银行、社交账号。A 站库泄露 = 用户所有账号沦陷。

所以行业标准是：**只存密码的哈希（单向摘要），永远不存明文**。

## 二、为什么 MD5 / SHA-256 不够

MD5 / SHA 这类通用哈希算法设计目标是**快**——为校验文件、签名设计，一秒能算几亿次。

在密码场景下，「快」反而是致命缺陷：

| 攻击方式 | 原理 | 为什么通用哈希扛不住 |
|---|---|---|
| 彩虹表 | 预先算好「常见密码 → 哈希」的巨型对照表，查表反推 | 无盐哈希对所有用户结果一致，一张表通吃 |
| 暴力破解 | 逐个试密码 | 算得太快，GPU 每秒可尝试数十亿次 |
| 字典攻击 | 只试常见密码组合 | 同上，快 = 试得多 |

密码哈希需要的是**慢**且**带盐**——这正是 bcrypt 的设计目标。

## 三、bcrypt 是什么

bcrypt 是 1999 年发布的**专用密码哈希算法**，基于 Blowfish 加密算法改造，内置三个关键特性：

1. **慢**：刻意设计成 CPU 密集型，单次哈希约 100ms 量级，GPU 加速效果有限
2. **内置盐**：自动生成随机盐并嵌入输出，同一密码每次哈希结果都不同
3. **可调成本**：硬件升级后可以调大计算量，保持破解成本

Node.js 生态有两个主流包：

- `bcrypt`：C++ 原生实现（本项目用的这个）
- `bcryptjs`：纯 JS 实现，无需编译但慢约 30%

## 四、核心概念 1：盐（Salt）

**盐 = 哈希前拼在密码上的随机字符串。**

```text
用户A 密码 "123456" + 盐A(随机) → 哈希X
用户B 密码 "123456" + 盐B(随机) → 哈希Y   ← 两个哈希完全不同
```

盐解决两个问题：

- **彩虹表失效**：同样的密码因盐不同产生不同哈希，无法查预计算表
- **相同密码不可见**：攻击者看库无法发现「用户A和用户B用的是同一个密码」

bcrypt 的盐是**自动生成、自动嵌入哈希串**的，不需要单独存一列——比对时 `compare` 会从哈希串里把盐解析出来。

## 五、核心概念 2：成本因子（Cost / Salt Rounds）

```ts
bcrypt.hash(password, 10)  // 10 就是 salt rounds（成本因子）
```

计算量随轮数**指数增长**：

| rounds | 单次耗时（参考值） | 说明 |
|---|---|---|
| 8 | ~25ms | 太快，不安全 |
| 10 | ~100ms | **业界默认，本项目用这个** |
| 12 | ~300ms | 更安全，登录稍慢 |
| 14 | ~1.2s | 高安全场景 |

设计意图：**让合法服务器的"一次登录"几乎无感，让攻击者的"十亿次尝试"贵到不可行**。

时间维度上也有说法——硬件每两年翻倍，可以定期调高 rounds（比如升到 12），用户下次登录时无缝 rehash。

## 六、哈希串结构解剖

```text
$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 │   │  │____________________________││____________________________│
 │   │            盐（22字符）                     哈希值（31字符）
 │   │
 │   └── 成本因子：2^10 = 1024 轮
 │
 └── 算法版本：2b（当前标准）

总长固定 60 字符，数据库 password 列 varchar(60) 即可
```

关键点：**盐和成本因子都存在哈希串里**。所以 `compare` 不需要额外参数，一切信息自包含。

## 七、本项目的用法

注册时（`auth.service.ts` → `register`）：

```ts
// 明文 → 哈希，10 轮
data.password = await bcrypt.hash(data.password, 10);
// 入库的是 "$2b$10$..." 60位字符串，明文不落库
return this.prisma.user.create({ data });
```

登录时（`auth.service.ts` → `login`）：

```ts
// 比对：明文 vs 库里的哈希
// ❌ 不能写 hash(明文) === userInfo.password —— 盐是随机的，两次 hash 必然不同
// ✅ compare 内部从哈希串解析出盐 + 轮数，用同样参数重算再比对
const ok = await bcrypt.compare(data.password, userInfo.password);
```

两条安全细节已经落地：

1. **用户不存在和密码错误返回同一种报错**（"邮箱或密码错误"），防止攻击者探测哪些邮箱已注册（用户枚举攻击）
2. **compare 是异步的**——100ms 的计算不该阻塞事件循环，不要用 `compareSync`

## 八、bcrypt vs argon2

| 维度 | bcrypt | argon2 |
|---|---|---|
| 发布时间 | 1999 | 2015（Password Hashing Competition 冠军） |
| 抗 GPU 攻击 | 一般（仍可 GPU 并行加速） | 强（同时吃内存，GPU 并行成本高） |
| 生态成熟度 | 极成熟，几乎所有框架内置 | 较新但主流化中 |
| 使用体验 | `bcrypt.hash / compare` | `argon2.hash / verify`，API 几乎同形 |

选型结论（对这个项目）：

- **bcrypt 足够**：教学项目 + 生态最成熟 + LEARNING_PLAN 里写的就是 bcrypt
- 如果新起生产项目，**argon2id 是更现代的选择**（OWASP 首选推荐）

## 九、常见坑

1. **用 `===` 比较两次哈希** —— 必然失败，盐是随机的。永远用 `compare`
2. **hash 存的列太短** —— 哈希串固定 60 字符，`varchar(60)` 起步，别用 `varchar(20)`
3. **rounds 写太小**（如 4）—— 几毫秒就完成，形同虚设；也别太大（如 16），登录要等十几秒
4. **注册接口没做唯一约束兜底** —— email 虽有 `@unique`，但注册冲突时应 catch P2002 抛 409，而不是让 500 冒出来
5. **同步 API 阻塞事件循环** —— `hashSync` / `compareSync` 会卡住整个 Node 进程 100ms，并发下直接雪崩。始终用 async 版本
6. **把哈希记进日志** —— 哈希虽不可逆但可被离线暴力破解，日志里只记 email，不记密码相关字段

## 十、面试可能问到的点

- **Q: 为什么 bcrypt 不能被彩虹表破解？**
  A: 每次哈希带随机盐，同一密码哈希结果不同，预计算表作废。

- **Q: 那盐存在哪里？需要单独一张表吗？**
  A: 不需要。盐直接嵌在哈希串前 22 字符里，`compare` 自解析，自包含。

- **Q: 登录时怎么知道用多少轮重算？**
  A: 同样从哈希串解析（`$2b$` 后面的数字），成本因子自描述。

- **Q: bcrypt 加密能解密回来吗？**
  A: 不能。bcrypt 是**哈希**不是**加密**——没有密钥、没有逆函数，只有"用同样输入重算一遍再比对"。这是密码存储和"加密存储"的本质区别。

- **Q: 用户改密码 / 数据库迁移时，怎么从旧哈希算法升级？**
  A: 常见做法是登录成功时检测旧格式（如无盐 MD5），立即用 bcrypt 重哈希静默更新（transparent rehash on login）。
