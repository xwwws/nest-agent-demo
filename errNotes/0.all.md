## 目标一 · Monorepo

### 1.1 概述

**Monorepo（单仓库）**：把多个相互关联的项目/包放在同一个 Git 仓库里统一管理。

| 对比项 | Monorepo | Polyrepo |
| --- | --- | --- |
| 代码位置 | 一个仓库多个包 | 一个仓库一个项目 |
| 依赖共享 | 本地包直接引用（`workspace:*`） | 需发 npm 包或拷贝代码 |
| 版本一致性 | 统一 lockfile | 各仓库独立，易漂移 |
| 典型工具 | pnpm workspace / Turborepo / nx | 无 |

**本项目选型**：`pnpm`（包管理 + workspace）+ `Turborepo`（任务编排）。

### 1.2 本项目结构

```
nest-demo/
├── apps/                 # 可独立部署的应用
│   ├── api/              # NestJS 后端
│   └── web/              # Next.js 前端
├── packages/types/       # 共享 TS 类型包（@agent-workspace/types）
├── pnpm-workspace.yaml   # 声明 workspace 范围
├── turbo.json            # 任务编排配置
└── pnpm-lock.yaml        # 统一锁文件
```

约定：`apps/` 放可独立运行的应用，`packages/` 放被复用的库。共享包用作用域命名 `@xxx/yyy`，避免与 npm 公共包冲突。

### 1.3 pnpm workspace

- **声明范围**：`pnpm-workspace.yaml` 里写 `packages: ["apps/*", "packages/*"]`，子目录有 `package.json` 即被识别为 workspace 包。
- **本地引用**：`web` 引用共享包写 `"@agent-workspace/types": "workspace:*"`，安装时 pnpm **软链接**到本地 `packages/types`，改了类型立即生效、无需发版。
- **统一管理**：根 `pnpm-lock.yaml` 锁全仓版本；公共工具（turbo）放根 `devDependencies`；`packageManager` 字段固定 `pnpm@11.23.0`。

### 1.4 Turborepo 任务编排

负责「在多个包里并行/按依赖顺序执行脚本」并做缓存。根 `package.json` 的 `dev/build/lint` 都是 `turbo xxx` 聚合。

`turbo.json` 关键字段：

| 字段 | 作用 |
| --- | --- |
| `dependsOn: ["^build"]` | `^` = 依赖的包；先构建依赖包，再构建自己 |
| `outputs` | 声明产物路径，用于缓存判断（产物没变就跳过） |
| `cache: false` | 关闭缓存（开发脚本通常关掉） |
| `persistent: true` | 常驻任务（`next dev` / `nest start --watch`），turbo 不等待其结束 |

依赖关系由各包 `dependencies`（含 `workspace:*`）自动推断，无需手动声明。

### 1.5 常用命令

| 命令 | 作用 |
| --- | --- |
| `pnpm install` | 安装全仓依赖（根目录） |
| `pnpm dev` / `pnpm build` / `pnpm lint` | 聚合执行所有包对应脚本 |
| `pnpm --filter api dev` | 只启动 `api` 包 |
| `pnpm --filter api add xxx` | 给 `api` 包添加依赖 |

> `--filter` 按包名/路径定位子包执行，日常开发单包时最常用。

### 1.6 易错点

1. 新建 workspace 包后要重新 `pnpm install` 才生成软链接。
2. 共享包引用写全名 `@agent-workspace/types`，别写 `types`。
3. `workspace:*` 只在 monorepo 内有效，未来发 npm 需改真实版本号。
4. `persistent: true` 必须给 dev 类常驻脚本，否则 `turbo dev` 会提前结束。
5. 全仓只用 pnpm，混用 npm/yarn 会导致 lockfile 不一致。

## 目标二 · Prisma 配置（Supabase）

### 2.1 Prisma 7 新变化

| 变化点 | 旧写法（≤6） | 新写法（7） |
| --- | --- | --- |
| 连接串位置 | `schema.prisma` 的 `datasource.url` | 移到 `prisma.config.ts` 的 `datasource.url` |
| client 生成器 | `prisma-client-js` | `prisma-client`（ESM + 自定义 output） |
| 查询引擎 | 内置 Rust binary engine | 需显式用 **driver adapter**（`@prisma/adapter-pg`） |

> 一句话：**连接串挪到 config，client 生成方式升级，运行时必须配 driver adapter。**

### 2.2 配置文件要点

- **schema.prisma**：`datasource` 只留 `provider = "postgresql"`，**不再写 `url`**；`generator` 用 `prisma-client`，`output = "../generated/prisma"` 把 client 生成到项目内便于 import。
- **prisma.config.ts**（本项目命名为 `prisma7.config.ts`）：用 `defineConfig` 定义，`datasource.url` 从这里注入；Prisma 7 **不再自动加载 `.env`**，顶部需手动 `import 'dotenv/config'`。

### 2.3 Driver Adapter 集成

`PrismaService` 继承 `PrismaClient`，构造时 `new PrismaPg({ connectionString })` 生成 adapter，`super({ adapter })` 传入：

| 点 | 说明 |
| --- | --- |
| 依赖 | `@prisma/adapter-pg` + 底层 `pg` |
| `super({ adapter })` | 用 adapter 连接，替代默认引擎 |
| 生命周期 | `OnModuleInit` 里 `$connect`，`OnModuleDestroy` 里 `$disconnect` |
| `@Global()` | `PrismaModule` 标 `@Global()`，全应用无需重复 import |

### 2.4 Supabase 连接

Supabase PostgreSQL 三种连接方式：

| 连接方式 | 端口 | 特点 |
| --- | --- | --- |
| Direct（直连） | 5432 | 无连接池，适合本地/迁移 |
| Transaction pooler | **6543** | pgBouncer 事务模式，适合无状态查询，不支持部分事务/Prepare |
| Session pooler | 5432 | pgBouncer 会话模式，支持完整会话，适合迁移 |

本项目 `.env` 两个连接串：

- **`DATABASE_URL`**：应用运行时用（走 pooler，带 `?schema=public`），缓解连接数压力。
- **`DIRECT_URL`**：`prisma migrate` 专用（session mode），因 transaction 模式可能中断迁移脚本。

### 2.5 迁移（migrations）

目录：`migrations/<时间戳>_init/migration.sql` + `migration_lock.toml`（锁 provider，勿手改）。

| 命令 | 作用 |
| --- | --- |
| `pnpm --filter api exec prisma generate` | 重新生成 client 到 `generated/` |
| `pnpm --filter api exec prisma migrate dev` | 开发：生成迁移 + 应用 |
| `pnpm --filter api exec prisma migrate deploy` | 生产：只应用已有迁移 |
| `pnpm --filter api exec prisma migrate status` | 查看迁移状态 |

### 2.6 易错点

1. 改 schema 必须重新 `prisma generate`，否则 client 类型/API 是旧的。
2. Prisma 7 不自动读 `.env`，config 顶部必须 `import 'dotenv/config'`。
3. `output` 路径相对 schema 文件（`../generated/prisma` 相对 `prisma/`）。
4. ESM 下 import 生成物要带 `.js` 后缀（`client.js`）。
5. 迁移用 `DIRECT_URL`，pooler transaction 模式会中断 migrate。
6. adapter 与 client 版本需一致（本项目均 7.10.0）。
7. `.env` 含敏感信息，务必 `.gitignore`。

## 目标三 · 用户模块 CRUD（NestJS + Prisma）

### 3.1 三层结构

| 文件 | 装饰器 | 职责 |
| --- | --- | --- |
| `users.module.ts` | `@Module()` | 组装 controller + service |
| `users.controller.ts` | `@Controller('users')` | 处理 HTTP 请求、路由、参数解析 |
| `users.service.ts` | `@Injectable()` | 业务逻辑、数据库操作 |

模块在 `app.module.ts` 的 `imports` 里引入才会被 Nest 加载。

### 3.2 路由与装饰器

| 装饰器 | 作用 | 示例 |
| --- | --- | --- |
| `@Controller('users')` | 定义路由前缀 | 所有路径拼在 `/users` 后 |
| `@Get()` / `@Post()` / `@Delete()` / `@Patch()` | 绑定 HTTP 方法 | — |
| `@Param('id')` | 取路径参数 | `/users/123` → `id = '123'` |
| `@Body()` | 取请求体（JSON） | `POST /users` 的 body |

### 3.3 依赖注入

`UsersService` 构造函数注入 `PrismaService`：

- `@Injectable()` 声明该类可被 Nest 容器管理（可注入、可被注入）。
- `constructor(private readonly prisma: PrismaService)` 是 TS 语法糖，同时声明私有只读属性并赋值，无需手动 `new`。
- 能直接注入，是因为 `PrismaModule` 标了 `@Global()` 且 exports 了它——全局模块无需每个业务模块重复 import。

### 3.4 Prisma CRUD

| 方法 | 作用 | 关键参数 |
| --- | --- | --- |
| `findMany()` | 查多条 | `where` / `orderBy` / `skip` / `take` |
| `findUnique()` | 按唯一字段查单条 | `where`（唯一字段，如 `id`、`email`） |
| `create()` | 新增一条 | `data` |
| `update()` | 更新一条 | `where` + `data` |
| `delete()` | 删除一条 | `where` |
| `upsert()` | 有则更新无则创建 | `where` + `create` + `update` |

这些方法由 Prisma 根据 `model User` 自动生成，返回 Promise（需 `await`）。

### 3.5 软删除模式

用 `isDelete` 布尔字段实现假删除：删除 = `update({ data: { isDelete: true } })`，恢复 = `update({ data: { isDelete: false } })`，数据始终保留。

| 对比 | 硬删除（`delete()`） | 软删除（`isDelete`） |
| --- | --- | --- |
| 数据 | 物理删除，不可恢复 | 保留，可恢复 |
| 用途 | 无需留痕 | 需审计/误删恢复 |
| 查询 | 直接查 | 需过滤 `isDelete: false` |

> 代价：查询/更新时要记得过滤 `isDelete`，否则「已删除」数据也会查出来。

### 3.6 待优化点

1. `@Body() data: any` → 换 DTO + `ValidationPipe`（项目已装 class-validator / class-transformer）。
2. `findAll` 未过滤软删除，应加 `where: { isDelete: false }`。
3. `findOne` 可换 `findUniqueOrThrow`，查不到抛 P2025 返回 404。
4. 未用 Prisma 生成的类型（`Prisma.UserCreateInput` 等），仍用 `any`。
5. 更新路由用 `@Post('/update/:id')`，更 RESTful 的是 `@Patch('/:id')`。

## 目标四 · Auth 模块（DTO 验证）

### 4.1 结构

认证模块负责「注册 + 登录」，三层结构与 users 一致，额外多了 `DTO/` 目录放入参定义（`auth.dto.ts`、`login.dto.ts`）。

### 4.2 DTO 定义（class-validator）

DTO 用 `class-validator` 装饰器声明校验规则：

| 装饰器 | 作用 |
| --- | --- |
| `@IsNotEmpty()` | 非空（`''`/`null`/`undefined` 都不通过） |
| `@IsString()` | 必须是字符串 |
| `@IsEmail()` | 必须是合法邮箱 |
| `@IsInt()` / `@IsNumber()` | 整数 / 数字 |
| `@Min(n)` / `@Max(n)` | 数值范围 |
| `@IsOptional()` | 字段可选（配合其他规则） |
| `@Length(min, max)` | 字符串长度范围 |

> 每个装饰器都支持 `{ message: '自定义文案' }` 覆盖默认报错。

### 4.3 class-transformer 转换

| 函数 | 作用 |
| --- | --- |
| `plainToClass(Cls, obj)` | 普通对象 → 类实例（触发装饰器） |
| `classToPlain(obj)` | 类实例 → 普通对象（序列化） |
| `validate(obj)` | 执行校验，返回错误数组 |

> 关键点：**装饰器只在「类实例」上生效**，直接校验普通对象会得到空结果，所以必须先 `plainToClass` 再 `validate`。

### 4.4 手动校验流程

当前 controller 写法：`接收 body → plainToClass 转实例 → validate 校验 → 有错返回 / 无错进 service`。

> 注意：当前失败分支返回 HTTP 200 + 错误对象，规范做法是抛 `BadRequestException`（见 4.5）。

### 4.5 全局 ValidationPipe（推荐）

手动校验是「教学写法」，地道做法是 `main.ts` 里 `app.useGlobalPipes(new ValidationPipe(...))`，让 `@Body()` 自动校验：

| 配置项 | 作用 |
| --- | --- |
| `whitelist: true` | 自动剔除 DTO 里没声明的字段 |
| `forbidNonWhitelisted: true` | 有未声明字段时直接报错 |
| `transform: true` | 自动把 body 转成 DTO 实例（省掉 plainToClass） |

| 对比 | 手动校验 | 全局 ValidationPipe |
| --- | --- | --- |
| 代码量 | 每接口重复写 | 零重复，装饰器声明即可 |
| 失败行为 | 手动返回（本例 200） | 自动抛 400 BadRequest |
| transform | 手动 | 自动转 DTO 实例 |

> 本项目 `main.ts` 目前**尚未注册 ValidationPipe**，所以 controller 里才手动校验，后续可补上。

### 4.6 bcrypt 密码处理

| 概念 | 说明 |
| --- | --- |
| `bcrypt.hash(明文, rounds)` | 生成带盐哈希；rounds 是成本因子（10 约 100ms） |
| 盐（salt） | 每次随机生成并嵌入结果，同密码两次 hash 不同 |
| `bcrypt.compare(明文, 哈希)` | 从哈希串解析盐和因子，重算再比对 |
| 为什么不能直接比 hash | 盐随机，`hash(明文) === 存的值` 永远不成立 |

> **安全细节**：登录时「用户不存在」和「密码错误」返回同一句「邮箱或密码错误」，防用户枚举攻击。

### 4.7 待优化点

1. 改全局 ValidationPipe（当前手动校验且失败返回 200）。
2. 登录成功应签发 JWT（现在只返回 message，Phase 2 接 `@nestjs/jwt`）。
3. DTO 命名不统一：`RegisterDTO` vs `LoginDto`，建议统一驼峰。
4. `LoginDto.email` 声明可选却配 `@IsNotEmpty()`，登录邮箱应必填。
5. `RegisterDTO.name` 强制非空，但 schema 里 `name String?` 可空，需对齐。
6. 密码强度不足，可加 `@MinLength(8)`。

## 目标五 · bcrypt 存储密码

> 深度原理手册见 `errNotes/2.bcrypt.md`，本块是浓缩版。

### 5.1 为什么不能明文/快速哈希

| 存储方式 | 问题 |
| --- | --- |
| 明文 | 库泄露 = 密码直接暴露，且用户常复用密码 |
| MD5 / SHA-256 | 设计目标是「快」，GPU 每秒可试数十亿次，扛不住暴力/彩虹表 |

**结论**：密码要存「慢 + 带盐」的哈希，这正是 bcrypt 的设计目标。

### 5.2 三个特性

bcrypt（1999，基于 Blowfish）是专用密码哈希算法：

1. **慢**：单次约 100ms，刻意 CPU 密集，GPU 加速有限。
2. **内置盐**：自动生成随机盐并嵌入输出，同密码每次结果不同。
3. **可调成本**：硬件升级后可调大计算量。

Node 生态两包：`bcrypt`（C++ 原生，快，需编译，本项目用）、`bcryptjs`（纯 JS，免编译，慢约 30%）。

### 5.3 盐（Salt）

**盐 = 哈希前拼在密码上的随机字符串。** 同密码 + 不同盐 → 完全不同哈希。解决两个问题：**彩虹表失效**、**相同密码不可见**。

> bcrypt 的盐自动生成、自动嵌入哈希串，无需单独存列，`compare` 会自解析。

### 5.4 成本因子（salt rounds）

`bcrypt.hash(password, 10)`，计算量随轮数指数增长：

| rounds | 单次耗时 | 说明 |
| --- | --- | --- |
| 8 | ~25ms | 偏快 |
| 10 | ~100ms | 业界默认，本项目用这个 |
| 12 | ~300ms | 更安全 |
| 14 | ~1.2s | 高安全场景 |

设计意图：合法登录几乎无感，攻击者「十亿次尝试」贵到不可行。

### 5.5 哈希串结构

```
$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 算法  成本   盐（22字符）        哈希值（31字符）
```

- `$2b` 算法版本，`$10` 成本因子（2^10 = 1024 轮）。
- 总长固定 **60 字符**，数据库列 `varchar(60)` 即可。
- 关键：盐和成本因子都自包含在哈希串里，`compare` 无需额外参数。

### 5.6 本项目用法

- 注册：`data.password = await bcrypt.hash(data.password, 10)`，落库的是 60 位哈希串。
- 登录：`const ok = await bcrypt.compare(明文, 哈希)`，从哈希串解析盐 + 轮数重算比对。

两条安全细节：

1. 用户不存在 / 密码错误返回同一句「邮箱或密码错误」，防用户枚举攻击。
2. 用异步 `compare` 而非 `compareSync`——100ms 计算不应阻塞事件循环。

### 5.7 常见坑

1. 用 `===` 比较两次哈希 → 必然失败，永远用 `compare`。
2. 密码列太短 → 哈希固定 60 字符，`varchar(60)` 起步。
3. rounds 太小/太大 → 4 形同虚设，16 登录要等十几秒。
4. 注册不兜底唯一冲突 → email `@unique` 冲突应 catch P2002 抛 409。
5. 同步 API 阻塞 → `hashSync` / `compareSync` 会卡住 Node 进程 100ms。
6. 哈希写进日志 → 可被离线爆破，日志只记 email 不记密码字段。

### 5.8 与 argon2 对比

| 维度 | bcrypt | argon2 |
| --- | --- | --- |
| 发布时间 | 1999 | 2015（密码哈希竞赛冠军） |
| 抗 GPU | 一般 | 强（吃内存） |
| 生态 | 极成熟 | 主流化中 |
| API | `hash/compare` | `hash/verify`（同形） |

**结论**：教学项目 + 生态成熟 → bcrypt 足够；新起生产项目 → 可选 argon2id（OWASP 首选）。

## 目标六 · JWT 鉴权（引入与签发）

> 本块聚焦「JWT 引入 + 登录签发 token」；鉴权守卫（Guard）与受保护路由见「目标七」。

### 6.1 JWT 是什么

JWT（JSON Web Token）：一种**无状态、自包含**的令牌，用于身份认证与信息传递。

| 对比 | Session（传统） | JWT |
| --- | --- | --- |
| 状态存储 | 服务端存 session（内存/Redis） | 无状态，服务端不存 |
| 扩展性 | 多实例需共享 session 存储 | 天生适合分布式 |
| 信息载体 | 只是一个 ID | token 内自带用户信息（payload） |
| 失效控制 | 服务端可主动销毁 | 无法主动失效，靠过期时间 |

### 6.2 JWT 结构（三段式）

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
 └──── Header ────┘ └────── Payload ──────┘ └──────────── Signature ──────────┘
```

| 段 | 内容 | 说明 |
| --- | --- | --- |
| Header | `{ alg: "HS256", typ: "JWT" }` | 声明签名算法 |
| Payload | 自定义数据（如 `sub`、`email`） | 载荷，**Base64Url 编码，非加密** |
| Signature | `HMACSHA256(header + "." + payload, secret)` | 用密钥签名，防篡改 |

> 关键：JWT 的 payload 是**编码不是加密**，任何人 Base64 解码就能看到内容，所以**绝不能放密码等敏感信息**。

### 6.3 签发与验证流程

```
登录成功
   ↓
JwtService.sign(payload) ── 用 JWT_SECRET 签名 ──→ 返回 token 给前端
   ↓
前端后续请求带 Authorization: Bearer <token>
   ↓
服务端用同一 JWT_SECRET 验签 → 通过则信任 payload，失败则 401
```

核心思想：**谁持有 secret，谁就能签发/验证**。secret 泄露 = 任何人可伪造 token。

### 6.4 @nestjs/jwt 引入

本项目已装 `@nestjs/jwt@^12.0.1`，`.env` 已配置：

| 变量 | 值 | 用途 |
| --- | --- | --- |
| `JWT_SECRET` | 随机长串（64 位 hex） | 签名密钥 |
| `JWT_EXPIRES_IN` | `7d` | token 有效期 |

引入方式：在 `AuthModule` 的 `imports` 里注册 `JwtModule`：

```ts
JwtModule.register({
  global: true,                 // 全局模块，其他模块无需重复 import
  secret: process.env.JWT_SECRET,
  signOptions: { expiresIn: '7d' },
})
```

要点：

- `global: true`：把 JwtModule 声明为全局模块，业务模块无需重复 import 也能注入 `JwtService`。
- `register`：同步读取配置，适合简单场景。
- `registerAsync`：异步加载（如从 ConfigService 读），工程化项目常用。
- 注册后 `JwtService` 可在同模块内注入使用。

### 6.5 签发 token（登录）

`AuthService` 注入 `JwtService`，登录成功后签发：

```ts
const jwtPayload: JwtPayload = { id, email, name }; // 自定义 payload 接口
const accessToken = await this.jwtService.signAsync(jwtPayload);
return { access_token: accessToken };               // 前端拿到后放 Authorization 头
```

| 要点 | 说明 |
| --- | --- |
| `sign(payload)` | 生成 token（同步） |
| `signAsync(payload)` | 异步版，推荐 |
| `JwtPayload` | 本项目自定义接口（id/email/name），统一 payload 类型 |
| `sub` vs `id` | JWT 规范建议 `sub` 放主体 ID，本项目直接用 `id`，前后端约定一致即可 |
| payload 内容 | 只放非敏感标识，**不放密码** |

> `expiresIn` 已在 `JwtModule.register` 统一配好，`sign` 时无需重复传。

### 6.6 易错点与注意

1. **secret 硬编码进代码**：必须放 `.env` + `.gitignore`，泄露可伪造任意身份。
2. **payload 放敏感信息**：JWT 可被 Base64 解码，密码/身份证号等绝不能放 payload。
3. **`expiresIn` 单位**：数字默认秒（`3600` = 1h），字符串 `"7d"` = 7 天，别写混。
4. **读 `process.env` 的时机**：`JwtModule.register` 在模块加载时执行，需确保 `dotenv/config` 已先加载，否则读到 undefined。
5. **到期前一直有效**：JWT 签发后无法主动失效，登出/踢人需黑名单或短过期 + refresh token。
6. **HS256 是同一密钥签名与验签**：secret 只存服务端，绝不发给前端。

## 目标七 · JWT 鉴权守卫（Passport）

> 承接目标六：登录已签发 token，本块用 Passport 完成「携带 token 访问受保护路由」的验签与身份注入。

### 7.1 为什么用 Passport

| 对比 | 手写 Guard | Passport |
| --- | --- | --- |
| 工作量 | 自己解析 header + verify | 策略声明式配置 |
| 生态 | 无 | 500+ 策略（jwt / local / github…） |
| 结构 | 全塞一个文件 | Strategy（验签）+ Guard（拦截）分离 |

本项目选 Passport：`@nestjs/passport` + `passport-jwt`，是 Nest 官方推荐的 JWT 鉴权方案。

### 7.2 JwtStrategy（验签策略）

`auth.strategy.ts` 继承 `PassportStrategy(Strategy)`，声明「从请求取 token + 验签」：

```ts
super({
  jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(), // 从 Authorization: Bearer 取
  ignoreExpiration: false,                                   // 不忽略过期
  secretOrKey: process.env.JWT_SECRET!,                      // 用同一密钥验签
});

validate(payload) { return payload; }  // 验签通过后，返回值挂到 req.user
```

| 配置项 | 作用 |
| --- | --- |
| `jwtFromRequest` | 指定从请求哪里取 token（常用 `fromAuthHeaderAsBearerToken`） |
| `ignoreExpiration` | `false` = 校验过期时间，过期即 401 |
| `secretOrKey` | 验签密钥，必须与签发时一致 |

> `validate(payload)` 的返回值会挂到 `req.user`，是「验签后把身份注入请求」的关键钩子。

### 7.3 JwtAuthGuard（守卫）

`jwt-auth.guard.ts` 只需一行，把策略名串起来：

```ts
export class JwtAuthGuard extends AuthGuard('jwt') {}
```

- `AuthGuard('jwt')` 里的 `'jwt'` 对应 `PassportStrategy` 的默认策略名（类名去掉 `Strategy` 转小写）。
- Guard 负责「要不要放行」，Strategy 负责「怎么验签」，两者协作。

### 7.4 使用：@UseGuards 保护路由

```ts
@Get('/profile')
@UseGuards(JwtAuthGuard)          // 该路由需带有效 token 才能访问
profile(@Req() req: any) {
  return req.user;                // validate 返回的 payload（id/email/name）
}
```

流程：请求带 `Authorization: Bearer <token>` → Guard 触发 JwtStrategy 验签 → 通过则 `req.user` 有值，失败则 401。

### 7.5 完整链路回顾

```
POST /auth/login ── signAsync 签发 access_token ──→ 返回给前端
                                                      ↓
GET /auth/profile + Authorization: Bearer <token>
                                                      ↓
JwtAuthGuard → JwtStrategy 验签（ExtractJwt + secretOrKey）
                                                      ↓
通过 → validate(payload) → req.user → controller 返回用户信息
失败 → 401 Unauthorized
```

### 7.6 易错点与注意

1. **签发与验签密钥必须一致**：`JwtModule.register` 的 `secret` 和 `JwtStrategy` 的 `secretOrKey` 必须用同一个 `JWT_SECRET`，否则验签必失败。
2. **策略名要对上**：`AuthGuard('jwt')` 的名字要与策略默认名一致（`JwtStrategy` → `'jwt'`）。
3. **`validate` 的返回值就是 `req.user`**：不要在 controller 里再手动 verify，Guard 已替你注入。
4. **`ignoreExpiration: false`**：别忘了关掉，否则过期 token 也能通过。
5. **`extractJwt` 方式**：前端 header 必须严格写成 `Authorization: Bearer <token>`（Bearer 后一个空格），否则提取失败。
6. **`validate` 里可做二次校验**：当前直接 `return payload`，生产可在此查库确认用户仍存在（如是否被禁用/软删除）。
