## 一、现象

NestJS 应用启动**完全正常**，路由也成功注册：

```text
LOG [RoutesResolver] UsersController {/users}:
LOG [RouterExplorer] Mapped {/users, GET} route
LOG [NestApplication] Nest application successfully started
```

但请求一进来，调用 Prisma 查询就炸：

```text
ERROR [ExceptionsHandler] PrismaClientKnownRequestError:
Invalid `this.prisma.user.findMany()` invocation in
/Users/wz/Desktop/wz/code/nest-demo/apps/api/src/users/users.service.ts:8:42

meta: {
  code: 'ECONNREFUSED',
  modelName: 'User',
  clientVersion: '7.10.0'
}
```

关键特征：

| 特征 | 说明 |
|---|---|
| 错误类型 | `PrismaClientKnownRequestError`（运行时，不是 TS 编译错） |
| 错误码 | `ECONNREFUSED`（TCP 层连接被拒） |
| 触发时机 | 应用启动正常，**发请求时**才报错 |
| 涉及模块 | `PrismaService` → `@prisma/adapter-pg` → Supabase PostgreSQL |

## 二、根因分析

### 根因一句话

**`.env` 里的 `DATABASE_URL` 根本没被加载进 `process.env`，`PrismaPg` 拿到 `undefined` 后静默回退到 `pg` 驱动默认值（`localhost:5432`），本机没有 Postgres，连接被拒。**

### 完整因果链

```text
apps/api/.env 文件里 DATABASE_URL 写得完全正确
        ↓
但 apps/api/src/main.ts 没有 import 'dotenv/config'
        ↓
NestJS 默认【不会】自动读取 .env 文件
        ↓
运行时 process.env.DATABASE_URL === undefined
        ↓
new PrismaPg({ connectionString: undefined })  ← 这里不报错！
        ↓
pg 驱动回退到默认连接参数：
  host: localhost
  port: 5432
  user: $USER（macOS 用户名）
  database: $USER
  password: 空
        ↓
本机没有运行 PostgreSQL
        ↓
ECONNREFUSED（连接被拒）
```

### 为什么容易误判

很多人第一反应是「数据库挂了 / 网络不通 / Supabase 连接串写错了」，然后去检查 Supabase 控制台、换端口、查防火墙——全部白费。因为**真正的连接串从头到尾就没被用到**。

### 为什么 prisma7.config.ts 里的 dotenv 不生效

`prisma7.config.ts` 开头确实写了 `import "dotenv/config"`，但它**只服务于 Prisma CLI 进程**：

| 进程 | 加载哪个文件 | 是否加载 .env |
|---|---|---|
| `prisma generate` / `prisma migrate` | `prisma7.config.ts` | ✅ 会加载 |
| `nest start --watch`（Nest 运行时） | `src/main.ts` | ❌ 不会加载 |

两个是**完全独立的进程**，各自有各自的模块加载链。CLI 那边配置正确，不代表运行时也对。

## 三、修复方案

`apps/api/src/main.ts` 顶部加一行（`dotenv@^17.4.2` 已在 dependencies，无需安装）：

```diff
+ import 'dotenv/config';
  import { NestFactory } from '@nestjs/core';
  import { AppModule } from './app.module';
```

注意：**必须放在第一行**。要保证在 `AppModule`（→ `PrismaModule` → `PrismaService` 构造函数读 `process.env`）被加载之前就把 `.env` 灌进环境变量。import 的副作用执行顺序是从上到下的，放后面就晚了。

## 四、验证方式

```bash
# 1. 重启 dev（turbo 会自动 watch 到 main.ts 变化并重启）
pnpm dev

# 2. 请求 users 接口（空表应返回 []）
curl http://localhost:3001/users
# 期望输出: []

# 3. 如果还想确认 DATABASE_URL 确实加载了，可在 PrismaService 构造函数里临时打印
console.log('DATABASE_URL loaded:', !!process.env.DATABASE_URL);
```

## 五、为什么坑这么深

三个因素叠加，让它成为"沉默故障"：

1. **`new PrismaPg({ connectionString: undefined })` 不抛错** —— pg 驱动把 undefined 当"用默认值"处理，合法且合理（很多场景就是想连本机 PG）
2. **Nest 启动照常成功** —— PrismaService 的 `onModuleInit → $connect()` 是懒连接池初始化，未必真正建 TCP 连接（取决于驱动实现），就算建了失败也可能只是 warning
3. **错误发生在离根因最远的地方** —— 请求 → Controller → Service → findMany → pg → localhost:5432 → 拒绝。从报错现场往回追 6 层才到 `.env` 没加载

## 六、预防措施（建议落地）

在 `apps/api/src/prisma/prisma.service.ts` 构造函数加前置校验，让问题**在启动瞬间就崩**，而不是等请求来撞墙：

```ts
constructor() {
  const url = process.env.DATABASE_URL;
  if (!url) {
    // 启动即崩，日志直接告诉你去查什么
    throw new Error(
      'DATABASE_URL is required. ' +
      '检查 apps/api/.env 是否存在，以及 main.ts 是否有 import "dotenv/config"',
    );
  }

  const adapter = new PrismaPg({ connectionString: url });
  super({ adapter });
}
```

经验法则：**任何从 `process.env` 读关键配置的地方，都应该在构造/启动阶段做存在性校验**（Fail Fast 原则）。晚暴露一分钟，排查成本翻十倍。

## 七、排查决策树（可复用）

下次遇到 Prisma 连接类报错，按这个顺序走：

```text
Prisma 连接报错
    ↓
【第一步】错误码是什么？
    ├── ECONNREFUSED → TCP 被拒，跳第二步
    ├── ETIMEDOUT / ENOTFOUND → 网络/DNS，检查网络和主机名
    ├── authentication failed → 用户名/密码错，检查连接串
    └── prepared statement / SAML 之类协议错 → PgBouncer 事务池兼容性
    ↓
【第二步】ECONNREFUSED：连的是【谁】？
    在 PrismaService 构造函数里打印 process.env.DATABASE_URL
    ├── undefined → .env 没加载（就是本案例）
    └── 有值但 host 是 localhost → 同样是没加载，pg 用了默认值
    ↓
【第三步】有值但连不上
    ├── host 是 pooler.supabase.com → 去 Supabase 控制台看项目是否被 pause
    ├── host 是 localhost → 本机 Postgres 起了吗？
    └── 再不行用 nc -zv <host> <port> 测网络连通性
```

## 附录：同一条链路上的另一个坑——nodenext 导入路径

同一个 `PrismaService` 在 2026-08-30 还报过三个 TS 编译错：

```text
TS2307: Cannot find module '../../generated/prisma'
TS2339: Property '$connect' does not exist on type 'PrismaService'
TS2339: Property '$disconnect' does not exist on type 'PrismaService'
```

### 根因

`tsconfig.json` 用 `module: nodenext` + `moduleResolution: nodenext`（严格 ESM），规则是：

- 相对路径导入**必须带显式 `.js` 后缀**
- 目录形式导入（如 `'../../generated/prisma'`）必须有 `package.json#exports` 或 `index.ts`，两者都没有就 TS2307

Prisma 7（generator `provider = "prisma-client"`）生成的客户端入口是 `generated/prisma/client.ts`，目录里**没有** `index.ts`。生成文件自己内部也是全程 `.js` 后缀（`./enums.js`、`./internal/class.js`），应用代码必须遵守同样的约定。

### 修复

```diff
- import { PrismaClient } from '../../generated/prisma';
+ import { PrismaClient } from '../../generated/prisma/client.js';
```

后两个 TS2339（`$connect` / `$disconnect` 找不到）是连锁反应——模块解析失败导致继承关系断裂，路径修好后自然消失：这两个方法声明在 `generated/prisma/internal/class.ts` 导出的 `PrismaClient` 接口里，`extends PrismaClient` 后可继承到。

### 两个坑的关系

```text
编译期（8-30 修）              运行期（8-31 修）
TS2307/TS2339                  ECONNREFUSED
     ↓                              ↓
import 路径不符合 nodenext      .env 没加载进 process.env
     ↓                              ↓
都发生在 PrismaService，但一个挡在编译期、一个藏在运行期
```

编译期的问题编译器会直接告诉你行号，运行期的问题只会在线上请求时暴露——这就是为什么运行期配置校验（Fail Fast）值得单独做。
