# 目标七 · JWT 鉴权守卫（Passport）

> 本章要做什么：在目标六已能签发 token 的基础上，用 Passport 的 `JwtStrategy` + `JwtGuard` 完成「携带 token 访问受保护路由」的验签与身份注入，并掌握用 `APP_GUARD` 注册全局守卫。

> 承接目标六：登录已签发 token，本块用 Passport 完成「携带 token 访问受保护路由」的验签与身份注入。

## 7.1 为什么用 Passport

| 对比 | 手写 Guard | Passport |
| --- | --- | --- |
| 工作量 | 自己解析 header + verify | 策略声明式配置 |
| 生态 | 无 | 500+ 策略（jwt / local / github…） |
| 结构 | 全塞一个文件 | Strategy（验签）+ Guard（拦截）分离 |

本项目选 Passport：`@nestjs/passport` + `passport-jwt`，是 Nest 官方推荐的 JWT 鉴权方案。

## 7.2 JwtStrategy（验签策略）

`auth.strategy.ts` 继承 `PassportStrategy(Strategy)`，声明「从请求取 token + 验签」：

```ts
super({
  jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(), // 从 Authorization: Bearer 取
  ignoreExpiration: false,                                   // 不忽略过期
  secretOrKey: process.env.JWT_SECRET!,                      // 用同一密钥验签
});

validate(payload) { return payload; }  // 验签通过后，返回值挂到 req.user
```

| 配置项 | 作用 |
| --- | --- |
| `jwtFromRequest` | 指定从请求哪里取 token（常用 `fromAuthHeaderAsBearerToken`） |
| `ignoreExpiration` | `false` = 校验过期时间，过期即 401 |
| `secretOrKey` | 验签密钥，必须与签发时一致 |

> `validate(payload)` 的返回值会挂到 `req.user`，是「验签后把身份注入请求」的关键钩子。

## 7.3 JwtGuard（守卫）

最简版只需一行，把策略名串起来：

```ts
export class JwtGuard extends AuthGuard('jwt') {}
```

- `AuthGuard('jwt')` 里的 `'jwt'` 对应 `PassportStrategy` 的默认策略名（类名去掉 `Strategy` 转小写）。
- Guard 负责「要不要放行」，Strategy 负责「怎么验签」，两者协作。

> 本项目实际用的是「注入 `Reflector` + 重写 `canActivate`」的增强版，目的是在全局守卫下放行公开路由，见「目标八」。

## 7.4 使用：@UseGuards 保护路由

```ts
@Get('/profile')
@UseGuards(JwtGuard)          // 该路由需带有效 token 才能访问
profile(@Req() req: any) {
  return req.user;                // validate 返回的 payload（id/email/name）
}
```

流程：请求带 `Authorization: Bearer <token>` → Guard 触发 JwtStrategy 验签 → 通过则 `req.user` 有值，失败则 401。

## 7.5 完整链路回顾

```
POST /auth/login ── signAsync 签发 access_token ──→ 返回给前端
                                                      ↓
GET /auth/profile + Authorization: Bearer <token>
                                                      ↓
JwtGuard → JwtStrategy 验签（ExtractJwt + secretOrKey）
                                                      ↓
通过 → validate(payload) → req.user → controller 返回用户信息
失败 → 401 Unauthorized
```

## 7.6 易错点与注意

1. **签发与验签密钥必须一致**：`JwtModule.register` 的 `secret` 和 `JwtStrategy` 的 `secretOrKey` 必须用同一个 `JWT_SECRET`，否则验签必失败。
2. **策略名要对上**：`AuthGuard('jwt')` 的名字要与策略默认名一致（`JwtStrategy` → `'jwt'`）。
3. **`validate` 的返回值就是 `req.user`**：不要在 controller 里再手动 verify，Guard 已替你注入。
4. **`ignoreExpiration: false`**：别忘了关掉，否则过期 token 也能通过。
5. **`extractJwt` 方式**：前端 header 必须严格写成 `Authorization: Bearer <token>`（Bearer 后一个空格），否则提取失败。
6. **`validate` 里可做二次校验**：当前直接 `return payload`，生产可在此查库确认用户仍存在（如是否被禁用/软删除）。

## 7.7 全局守卫（APP_GUARD）

前面 7.4 的 `@UseGuards(JwtGuard)` 是「按路由手动挂」；若要**所有路由默认都要鉴权**，用 `APP_GUARD` 注册为全局守卫。

在 `app.module.ts` 注册：

```ts
providers: [
  {
    provide: APP_GUARD,     // 全局守卫注入点（@nestjs/core 常量）
    useClass: JwtGuard,     // 用哪个类做全局守卫
  },
  JwtGuard,                 // ⚠️ 必须同时声明为 provider，否则解析不到
  AppService,
],
```

| 配置项 | 说明 |
| --- | --- |
| `provide: APP_GUARD` | Nest 内置 token，代表「全局守卫」注入点 |
| `useClass: JwtGuard` | 全局守卫用哪个实现类 |
| 同时声明 `JwtGuard` | `useClass` 引用 ≠ 注册，类本身也要进 providers |

> **踩坑**：`useClass` 不会自动把被引用的类注册为 provider。若 `JwtGuard` 没进 `providers`，启动即报 `Nest could not find JwtGuard element`——因为它还依赖 `Reflector`，Nest 必须在 provider 池里能解析到它。

配套知识：

- **同类全局注入点**：`APP_PIPE`、`APP_FILTER`、`APP_INTERCEPTOR`（全局管道/异常过滤器/拦截器），套路一致：`provide: XXX` + `useClass`，被引用类需是 provider。
- **公开路由**：全局守卫下登录/注册也会被拦，已用 `@Public()` 装饰器 + `Reflector` 读 `SetMetadata` 放行，完整实现见「目标八」。
